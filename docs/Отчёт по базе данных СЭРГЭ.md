## Введение

Веб-платформа «СЭРГЭ» предназначена для выбора проекта частного дома, предварительной оценки затрат и сопровождения строительства в Якутии. Посетитель может изучить каталог и выполнить расчёт, затем оставить заявку. После начала работы клиент получает доступ к сведениям об объекте, его текущем этапе и опубликованным обновлениям.

Цель отчёта — описать реализованную базу данных и показать, как её таблицы используются в этих сценариях. Для этого рассматриваются состав и назначение таблиц, первичные и внешние ключи, жизненный цикл заявки и строительного объекта, настройка серверной версии и контрольные сценарии.

База рассчитана на MySQL 5.7 и выше либо MariaDB 10.3 и выше. Таблицы создаются с движком InnoDB и кодировкой utf8mb4. Серверный код PHP подключается к базе через PDO. Схема определяется в database/schema.sql, а начальные данные загружаются из database/seed.sql.

Публичный контент и данные сопровождения имеют разные требования к хранению. Каталог и исходные расценки могут загружаться из файлов JSON. Заявки, учётные записи и сведения о строительстве записываются в БД. Это позволяет сохранить публичный доступ к информации при недоступном подключении и хранить историю работы с конкретным клиентом на сервере.

## I. Состав базы данных

### 1.1. Настройки расчёта и каталог

**Таблица 1. Справочники и каталог**

| Таблица и ключ | Назначение и основные поля |
| --- | --- |
| settings — name | Параметры калькулятора. value хранит строку, которую PHP преобразует в нужный тип. Имена: area_min, area_max, floors_max, delta, round_step, k_reg, k_floors_many и date. |
| materials — code | Справочник материалов стен. Поле price задаёт ставку в рублях за 1 м² общей площади дома. sort_order определяет порядок в списке, is_active — доступность для расчёта. |
| foundations — code | Справочник фундаментов. Поле price задаёт ставку в рублях за 1 м² площади застройки. Порядок и доступность определяются так же, как у материалов. |
| houses — id | Карточка проекта. Хранит название, площадь, этажность, число спален и санузлов, коды материала и фундамента, признаки гаража и террасы, описание и пути к изображениям. |

Цена проекта в houses не хранится. При формировании каталога PHP вычисляет её по площади, этажности и ставкам из справочников. Поэтому изменение ставки влияет на новые расчёты и цены в каталоге без редактирования карточек.

Поле `is_published` управляет включением карточки в публичную выдачу, а `sort_order` определяет её позицию. Материал и фундамент в карточке обязательны. Внешний ключ проверяет существование записи справочника. Активность справочника и наличие его кода в наборе расценок проверяются отдельно на уровне приложения.

### 1.2. Контент сайта и учётные записи

**Таблица 2. Публикации и пользователи**

| Таблица и ключ | Назначение и основные поля |
| --- | --- |
| stages — id | Справочник этапов. title и short задают название и краткое описание. text содержит подробности, time — срок в текстовом виде, sort_order — порядок отображения. |
| journal_posts — id | Публикации журнала. slug используется в адресе статьи и имеет ограничение UNIQUE. Хранятся заголовок, анонс, изображение, категория, время чтения, текст, дата и признак публикации. |
| company_info — k | Блоки страницы компании. Значение v хранится в MEDIUMTEXT в формате JSON. Ключами обозначаются описание, показатели, принципы, команда, контакты и примечание. |
| users — id | Учётные записи клиента и администратора. Содержит роль, имя, контактные данные, хеш пароля, признак активности, поля подтверждения почты и даты создания и последнего входа. |

В users поля phone и email допускают NULL. Ограничения UNIQUE запрещают повтор конкретного номера или адреса, при этом учётные записи могут иметь незаполненный контакт соответствующего типа.

Для подтверждения почты используются хеш токена `email_token`, срок `email_token_expires` и дата `email_verified_at`. Поле `must_change_password` обозначает необходимость смены выданного пароля. `created_via` фиксирует способ создания записи: самостоятельная регистрация, действие администратора или установка. Тариф free или vip хранится как свойство пользователя.

### 1.3. Заявки, объекты и служебные данные

**Таблица 3. Рабочие и служебные таблицы**

| Таблица и ключ | Назначение и основные поля |
| --- | --- |
| leads — id | Обращение с именем, телефоном, почтой, сообщением и источником. params хранит параметры расчёта в JSON. user_id допускает NULL. Имеются статус, заметка администратора, сведения о согласии и даты создания и изменения. |
| objects — id | Строительный объект клиента. code — уникальный код. Хранятся пользователь, необязательный проект дома, название, адрес, номер договора, статус, текущий этап, готовность и даты. |
| object_updates — id | Сообщения о ходе работ. Каждое связано с объектом, может ссылаться на этап и содержать фото. is_visible определяет видимость клиенту, created_at — время публикации записи. |
| rate_limits — id | События ограничения частоты. bucket обозначает группу действий, k хранит хеш ключа, created_at — время в секундах Unix. |
| audit_log — id | Журнал действий администрации. Хранит идентификатор пользователя, действие, тип и идентификатор сущности, подробности и время. |

Таблица leads хранит самостоятельную запись обращения. Телефон в ней обязателен, поскольку используется для обратной связи, а учётная запись может отсутствовать. Поля `consent_at` и `consent_version` связывают заявку с моментом согласия и редакцией текста, показанной посетителю.

Объект строительства принадлежит одному пользователю. В objects хранится сводное состояние, а в `object_updates` — несколько событий по одному объекту. Такое устройство позволяет показать текущий прогресс отдельно от истории работ.

## II. Связи и целостность данных

### 2.1. Внешние ключи

У каждой из восьми связей кратность «один ко многим». Одна запись родительской таблицы может использоваться в нескольких дочерних строках, а каждая дочерняя строка по конкретному ключу ссылается максимум на одну родительскую.

**Таблица 4. Внешние ключи и действия при удалении**

| Дочернее поле | Родительский ключ | При удалении |
| --- | --- | --- |
| houses.material_code | materials.code | Запрет при наличии ссылок |
| houses.foundation_code | foundations.code | Запрет при наличии ссылок |
| leads.user_id | users.id | SET NULL |
| objects.user_id | users.id | CASCADE |
| objects.house_id | houses.id | SET NULL |
| objects.current_stage_id | stages.id | SET NULL |
| object_updates.object_id | objects.id | CASCADE |
| object_updates.stage_id | stages.id | SET NULL |

Обязательными являются ссылки `houses.material_code`, `houses.foundation_code`, `objects.user_id` и `object_updates.object_id`. В остальных случаях допускается NULL. Каскадное обновление предусмотрено для ссылок houses на материалы и фундаменты, а также для ссылки `objects.house_id` на каталог.

Удаление клиента приводит к удалению его объектов и их обновлений, а заявки сохраняются с пустым `user_id`. Удаление проекта дома сохраняет существующий строительный объект и очищает его `house_id`. При удалении этапа сведения об объекте и событиях сохраняются без ссылки на этот этап.

### 2.2. Индексы и ограничения

**Таблица 5. Индексы рабочих и служебных таблиц**

| Индекс и поля | Назначение |
| --- | --- |
| idx_leads_status (status, created_at) | Выборка заявок по статусу и дате создания. status стоит первым и задаёт группу записей. |
| idx_leads_phone (phone) | Поиск обращений по телефону. Один номер может встречаться в нескольких заявках. |
| idx_upd_obj (object_id, created_at) | Выборка событий конкретного объекта по времени. |
| idx_rl (bucket, k, created_at) | Поиск событий по группе, хешу ключа и временному интервалу. |
| idx_audit (created_at) | Выборка записей журнала за период. |

Первичный ключ идентифицирует запись. В справочниках материалов и фундаментов эту роль выполняет текстовый code, а в заявках, объектах и обновлениях — целочисленный id с AUTO_INCREMENT. В objects поле code имеет отдельное ограничение UNIQUE и используется как код объекта.

Ссылочная целостность и правила приложения решают разные задачи. Например, тип TINYINT в поле `objects.progress` задаёт способ хранения числа, а диапазон от 0 до 100 указан в схеме как предметное правило. Внешний ключ проверяет существование этапа, но сам по себе не определяет, соответствует ли этот этап статусу объекта.

В `audit_log.user_id` внешний ключ отсутствует. Поэтому удаление записи users не меняет автоматически это поле. В полях `leads.params` и `company_info.v` JSON хранится как текст. Разбор вложенных значений выполняется PHP, а перечисления ENUM ограничивают допустимые значения ролей и статусов на уровне схемы.

## III. Работа с данными в приложении

### 3.1. Каталог и контрольный расчёт

Публичные страницы обращаются к includes/repository.php. repo_houses() читает опубликованные проекты и упорядочивает их по sort_order и id. repo_rates() загружает настройки из settings, а ставки — из активных строк materials и foundations. Карточки каталога и серверный API калькулятора используют общую функцию raschet().

Функция proverka() проверяет диапазон площади, целое число этажей и наличие кодов материала и фундамента в текущем наборе ставок. По начальным данным допустимая площадь составляет от 10 до 1000 м², а этажность — от одного до трёх этажей. После проверки площадь застройки вычисляется делением общей площади на количество этажей.

**Таблица 6. Пример расчёта для проекта «СЭРГЭ 120»**

| Показатель | Вычисление и результат |
| --- | --- |
| Площадь застройки | 120 м² ÷ 2 = 60 м² |
| Стены из газобетона | 120 × 35 000 = 4 200 000 руб. |
| Свайно-ростверковый фундамент | 60 × 15 000 = 900 000 руб. |
| Базовая сумма | 4 200 000 + 900 000 = 5 100 000 руб. |
| Итог с коэффициентами | 5 100 000 × 1,15 × 1 = 5 865 000 руб. |
| Диапазон с отклонением 5 % | От 5 571 800 до 6 158 300 руб. |

В примере использованы демонстрационные ставки из `seed.sql`. Итог и границы приводятся к шагу 100 руб. Расчёт даёт предварительный ориентир до составления сметы по конкретному объекту.

### 3.2. Заявка, личный кабинет и администрирование

При отправке заявки сервер проверяет параметры и пересчитывает итог. В leads остаются контакты, источник и параметры обращения с рассчитанной суммой. Изменение справочников влияет на новые расчёты, а сохранённая запись остаётся прежней.

Заявка получает статус new. Статусы `in_work`, deal, rejected и spam обозначают обращение в работе, сделку, отклонённое и нежелательное обращение. При привязке к клиенту заполняется `user_id`.

Кабинет показывает объекты вошедшего пользователя. Статусы design, building и done соответствуют проектированию, строительству и завершению. Текущий этап берётся из stages, а обновления выводятся из `object_updates` с учётом `is_visible`.

Роли client и admin разграничивают доступ. Действия администрации записываются в audit_log, события ограничения частоты — в rate_limits. Слой includes/db.php передаёт значения в подготовленные запросы PDO отдельно от SQL.

### 3.3. Резервный источник данных

При выключенном USE_DB или невозможности подключиться repository.php читает публичные данные из data/*.json. Ставки также загружаются из rates.json, если SQL-выборка не сформировала набор активных материалов и фундаментов. Заявки, кабинеты и администрирование требуют подключения. Статическая сборка для GitHub Pages использует публичные страницы и расчёт в браузере.

## IV. Развёртывание и проверка

### 4.1. Первоначальная установка

1. Создать в phpMyAdmin базу serge со сравнением utf8mb4_unicode_ci.
2. Импортировать database/schema.sql, затем database/seed.sql. Первый файл создаёт таблицы и ограничения. Второй загружает исходные проекты, ставки, этапы и материалы сайта из данных, подготовленных скриптом tools/make-seed.php.
3. Создать includes/config.local.php по образцу config.local.php.example, настроить подключение, USE_DB и SETUP_KEY.
4. Открыть `install.php`, ввести установочный ключ и создать первую административную учётную запись. Проверить доступ к панели и загрузку каталога.

CREATE TABLE IF NOT EXISTS создаёт отсутствующие таблицы. Для обновления существующей структуры применяются указания README.txt. Повторный импорт `seed.sql` может изменить поля из ON DUPLICATE KEY UPDATE.

### 4.2. Проверка структуры

SHOW TABLES позволяет проверить наличие 13 таблиц. SHOW CREATE TABLE objects показывает структуру и внешние ключи объекта, а SHOW INDEX FROM leads — индексы заявок. Всего в схеме восемь внешних ключей.

В тестовой базе создаются опубликованный проект, клиент, его объект и два обновления с разной видимостью. Сценарии описаны в таблице 7.

### 4.3. Контрольные сценарии

**Таблица 7. Контроль после развёртывания**

| Проверка | Ожидаемый результат |
| --- | --- |
| Каталог | Опубликованный проект виден на сайте. После снятия публикации он исчезает из публичной выдачи. |
| Расчёт | Для 120 м², двух этажей, газобетона и свайно-ростверкового фундамента при начальных ставках итог составляет 5 865 000 руб. Площадь за пределами диапазона отклоняется. |
| Заявка | Обращение с согласованными данными сохраняется со статусом new. Для заявки из калькулятора заполнено params. |
| Личный кабинет | Клиент видит свой объект и его видимое обновление. Чужой объект и скрытое сообщение в выдачу не попадают. |
| Действия внешних ключей | При удалении тестового клиента его объект и обновления удаляются, а заявка сохраняется с NULL в user_id. |
| Резервный режим | При отключённой базе каталог открывается из JSON. Для операций с заявками и кабинетом требуется восстановить подключение. |

Сценарии проверяют разные уровни системы: расчёт и валидацию, доступ к данным по роли и владельцу, физические ограничения БД и работу резервного публичного источника. Таблица содержит ожидаемые результаты для проверки после установки.

## Заключение

База данных «СЭРГЭ» содержит 13 таблиц. Справочники и параметры калькулятора используются для оценки стоимости, каталог описывает типовые проекты, а заявки сохраняют контакты и расчёт, с которым обратился посетитель. Данные объекта и отдельные записи обновлений позволяют показывать клиенту текущее состояние и ход работ.

Восемь внешних ключей определяют обязательные ссылки и действия с дочерними записями. Проект каталога и этап могут быть удалены с сохранением строительного объекта. При удалении учётной записи история обращений остаётся доступной в заявках, а связанные строительные объекты и обновления удаляются каскадно.

Подготовленная структура разворачивается импортом схемы и начальных данных с последующей настройкой PDO-подключения. Публичный каталог и калькулятор могут использовать данные JSON. Приём заявок, учётные записи и управление объектами работают в серверной версии с базой данных.
